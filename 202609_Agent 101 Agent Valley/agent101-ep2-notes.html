这个 Lab 讲什么？

Agent 101 Week 2 · The Buildyard · ~1 小时完成

一句话总结：单个 Agent 无法完成整个任务。这个 Lab 教你把多个 Agent 和函数 串起来——决定谁先跑、谁并行跑、谁根据结果决定下一步。

场景故事：Agent Valley 的建筑工地

你是 Agent Valley 的设计师，要为一块地设计小屋 (cottage)。这不是一个人能完成的工作：

  • 地质专家 需要调查地基（计算土壤承重）
  • 仓库管理员 需要查库存有哪些建材
  • 气象分析师 需要分析当地气候，决定屋顶坡度和朝向
  • 设计师 汇总三方结论，生成设计图
  • 审核员 检查材料承重是否匹配，如果不行则打回重做

Lab 的核心是：只改 yard/agent.py 底部的 edges 列表，每次取消一行注释（删掉 # ），观察 workflow 如何改变。

💡 Lab 的精妙设计
整个 Lab 只需要编辑 三行代码（每次取消一行注释）。这不是偷懒——它是刻意的设计：让你专注于理解结构，而不是被语法细节分心。

核心问题：谁决定下一步？

Workflow 设计的根本问题

Lab 的灵魂问题：在一个多步骤任务里，谁来决定接下来运行哪个节点？答案不同，workflow 的能力和风险也完全不同。

三种答案，三种模式

模式 1 — Graph 定义

由边（edges）决定

你在代码里写好 edges 列表，执行顺序完全由图结构决定。运行时不会"思考"，只跟着边走。

  • ✅ 保证执行顺序，不会跳步
  • ✅ 可预测、可测试
  • ❌ 灵活性有限，路径需提前写死
模式 2 — 模型驱动

由 LLM 决定

让语言模型根据上下文判断下一步走哪个分支。Chapter 4 的字典路由就是这种——inspect 节点输出 "rework" 或 "pass"，由模型的回答决定走哪条路。

  • ✅ 智能灵活，能处理复杂判断
  • ❌ 失去执行保证（模型可能选错路）
  • ❌ 结果不完全可预测
模式 3 — 代码编排

由 Python 逻辑决定

用 Python 代码（if/else、循环等）动态决定执行路径，不依赖 edges 列表。

  • ✅ 最灵活，可以做任何动态分支
  • ❌ 没有自动暂停/恢复（crash 后无法续跑）
  • ❌ 需要自己管理状态
⚠️ 关键心智模型
选模式不是选"最强的"，而是选"最匹配你的可预测性需求"的。金融交易流程要用模式 1（不能让 LLM 随意决定是否扣款）；创意写作助手可以用模式 2（灵活更重要）。

Chapter 2 — 顺序执行

Edit 1 取消注释 blueprint,

一个边 = 一条数据通道。把两个节点用边连接，上游的输出自动成为下游的输入。

做什么改动

打开 yard/agent.py，找到文件末尾的 edges 列表，取消 blueprint, 前的注释：

# 改前
edges = [
    survey,
    # blueprint,   # ← 这行被注释掉了
]

# 改后（删掉 "# "）
edges = [
    survey,
    blueprint,     # ← 现在加入了
]

执行流程变化

改前（只有 survey）
START → survey → END
改后（survey → blueprint）
START → survey → blueprint → END
survey 的输出自动沿边流入 blueprint 的输入

关键理解

数据自动流动

不需要手动把 survey 的结果传给 blueprint。边（edge）本身就是数据通道——上游节点完成后，结果自动沿边流向下游节点。

节点类型无关

无论节点是 Agent（调用 LLM 的）、普通 Function（纯 Python 计算），还是带工具的 Agent，在 edges 列表里的写法完全一样——把名字放进去就行。

✅ 可以观察到什么
运行后你会看到设计图里多了蓝图内容：survey 调查了地基情况，blueprint 拿到这个结果后画出了初始设计草图。两步是严格顺序的——survey 100% 完成后才启动 blueprint。

Chapter 3 — 并行分支

Edit 2 取消注释 (ground, stock, weather), join, render, inspect,

括号 = 同时跑。把多个节点用 () 括起来，ADK 会并行启动它们，用 join 节点收集所有结果。

做什么改动

# 改前
edges = [
    survey,
    blueprint,
    # (ground, stock, weather), join, render, inspect,
]

# 改后
edges = [
    survey,
    blueprint,
    (ground, stock, weather), join, render, inspect,
]

执行流程

START → survey → blueprint
↓ 并行启动
ground 土壤计算
（Python 函数）
⋮
stock 查库存
（带工具的 Agent）
⋮
weather 气候分析
（Agent）
↓ 全部完成后汇聚
join → render → inspect → END
三个分支完成速度不同，join 等待最慢的那个

三个并行节点的不同类型

节点类型做什么为什么能并行
ground 普通 Python 函数 土壤承重算术计算（确定性） 纯计算，不依赖其他节点
stock 带工具的 Agent 查询建材库存 查询外部数据，独立的
weather Agent 分析气候数据 分析外部数据，独立的

join 节点怎么工作

Join 的输出格式

join 节点等待所有并行分支完成，然后把它们的结果合并成一个列表，每条结果都带有来源标签：

[
  { "branch": "ground", "result": "需要石基，深度 60cm..." },
  { "branch": "stock",  "result": "有花岗岩 200 块，木材 50 根..." },
  { "branch": "weather","result": "年均降水 1200mm，建议坡度 35°..." }
]

下游节点（render）拿到这个列表，才能综合三方信息生成设计图。

⚠️ 并行不是万能的
Lab 特别强调：三个相同的 prompt 不应该并行，那只是浪费，该合并成一个调用。并行的价值在于分支"本质不同"——不同工具、不同数据源、不同专长。
✅ 可以观察到什么
三个分支完成的时间不同（ground 是纯计算所以最快，weather/stock 需要 LLM 调用）。设计图会因库存和气候数据不同而变化——用石基还是抬高基础，坡度多少度。

Chapter 4 — 条件路由

Edit 3 取消注释 {"rework": stock, "pass": finish},

字典 = 路口。节点的输出决定走哪条路——"pass" 走向完成，"rework" 打回重新调查。

做什么改动

# 改前（inspect 只是结束）
edges = [
    ...
    inspect,
]

# 改后（inspect 后面接路由字典）
edges = [
    ...
    inspect,
    {"rework": stock, "pass": finish},
]

执行流程（含循环）

inspect → 路由字典
"rework" → stock
"pass" → finish
如果材料不匹配
stock
重新查库存 → 继续 render → inspect…
如果设计合格
finish
输出最终设计图 → END
inspect 输出的文字内容决定走哪条分支

路由的工作原理

inspect 节点如何触发路由

inspect 是一个 Agent，它的 prompt 要求它在回答末尾输出 rework 或 pass 这个关键词。ADK 读取这个关键词，然后查字典决定下一个节点：

# 字典的语义
{
  "rework": stock,   # inspect 说 "rework" → 跳回 stock 节点
  "pass":   finish,  # inspect 说 "pass"   → 走向 finish 节点
}

这是模型驱动路由——最终是 LLM 的输出决定走哪条路，不是代码的 if/else。

循环的意义

当 inspect 输出 "rework"，执行流会跳回 stock，然后重新经过 render 和 inspect。这形成了一个反馈循环：

  • 三个专家意见有冲突时（例如库存没有气候要求的防水材料），自动触发重新调查
  • 这是 agent workflow 的核心能力之一——自我纠错
  • Loop 直到 inspect 满意为止（实际代码会设置最大循环次数防止死循环）
💡 字典路由 vs. 边列表
普通边（edges 里的名字）是"必然走这条路"。字典是"根据结果走不同的路"。两者可以混用——在同一个 edges 列表里，顺序项和字典项交替出现。

数据如何在节点间流动

理解 edges 传值 vs. state 共享

ADK 有两种数据通道：节点之间用边自动传值，节点内部用 tool_context.state 共享状态。搞清楚这两条通道，就能写出干净的 workflow。

通道 1 — 沿边传值（节点间）

Edge Data Flow

当一个节点完成并有输出结果时，ADK 自动把这个结果传给 edges 列表里的下一个节点作为输入。

# survey 的输出 → 自动成为 blueprint 的输入
edges = [survey, blueprint]

# 不需要手动写：
# result = await survey.run()
# await blueprint.run(input=result)   ← ADK 帮你做了这步

并行分支（tuple）的每个分支各自拿到上游的相同输出，完成后统一交给 join。

通道 2 — tool_context.state（节点内部）

State Dict

在同一个节点内部（Agent 和它的工具之间），用共享字典 tool_context.state 交换数据。

# 工具写入 state
def check_stock(tool_context):
    result = query_inventory()
    tool_context.state["available_materials"] = result
    return result

# 同一节点的另一个工具读取 state
def calculate_cost(tool_context):
    materials = tool_context.state["available_materials"]
    # 用已有的库存数据计算成本，不用再查一次

State 是节点内部的"便签纸"，代码读、模型只能通过工具间接影响它。

对比总结

维度边传值（Edge）状态字典（State）
作用域节点与节点之间节点内部（Agent ↔ 工具）
触发时机节点完成时自动传递工具执行时主动读写
谁可见下游节点的 prompt/输入同一节点内的代码
典型用途把调查结论传给设计节点工具间共享中间计算结果
✅ 实践原则
边用于"阶段成果"，state 用于"工具协作"。设计 workflow 时先画出节点图和边，再考虑每个节点内部的工具怎么配合——两层分开设计，思路更清晰。

三种模式对比 & 选择指南

什么场景用什么模式

这三种模式不是进化关系——不是"条件路由比顺序执行更高级"。它们是不同场景的不同工具，选错了反而是负担。

完整对比表

模式edges 写法谁决定路径优势风险
顺序 A, B, C 图结构（确定性） 可预测，易调试 不灵活
并行 (A, B, C), join 图结构（同时启动） 省时间，分工明确 分支必须真正独立
条件路由 {"x": A, "y": B} 上游节点的输出内容 能循环，能自纠错 路径不完全可预测

选择指南

用顺序执行，当……
  • 步骤 B 必须依赖步骤 A 的结果
  • 流程不能跳步（合规、金融、审批流）
  • 你需要完全可预测的执行记录
用并行执行，当……
  • 多个任务之间没有依赖关系
  • 各分支需要不同的工具或外部数据源
  • 时间是瓶颈（三个 5 秒的任务 → 5 秒而不是 15 秒）
  • ⚠️ 不要把同样的 prompt 并行三次——那是浪费，合成一次调用
用条件路由，当……
  • 需要"如果不对就重做"的自纠错能力
  • 分支路径由业务逻辑（而不是随机因素）决定
  • 你能接受路径不完全确定（模型输出驱动）
  • 需要有限循环（记得设最大迭代次数）
💡 Lab 的核心金句
"一个 callback 管理一个 Agent 叫控制；同样的纪律应用到五个 Agent 上叫架构。"

Workflow 的本质：把单点控制能力（callback、边、路由字典）扩展到整个系统——这才是从写 Agent 到设计 Agent 系统的跨越。

关键代码速查

Lab 核心语法一览

edges 列表语法总结

# 顺序：逗号分隔
edges = [a, b, c]
# 执行顺序: a → b → c

# 并行：括号包裹
edges = [a, (b, c, d), join, e]
# 执行顺序: a → (b ‖ c ‖ d 同时) → join → e

# 条件路由：字典
edges = [a, {"ok": b, "fail": c}]
# a 的输出若含 "ok" → b；若含 "fail" → c

# 混合使用（本 Lab 最终形态）
edges = [
    survey,
    blueprint,
    (ground, stock, weather), join, render, inspect,
    {"rework": stock, "pass": finish},
]
