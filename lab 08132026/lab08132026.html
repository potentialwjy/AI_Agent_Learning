Understand the Agent

Know what you're deploying before you containerize it.

This agent uses the A2A (Agent-to-Agent) protocol — Google's open standard for agent interoperability. It exposes a standard HTTP interface at /.well-known/agent.json that any A2A-compatible client can discover.

Key files

app/main.py
A2A server entry point — reads PORT from env, registers health-check endpoint, starts uvicorn
app/agent.py
LangGraph agent loop — Claude 4.5 Sonnet model, system prompt, multi-turn conversation with tools
app/mcp_tools.py
MCP tool loader — switches between mock data (IBD_TESTING=1) and real Agent Gateway. This is your production/dev toggle.
app/skills/
Markdown skill files loaded at runtime — business logic without code changes

Why this agent is already Cloud Run-friendly

✓
Reads PORT from env — Cloud Run injects PORT=8080 at runtime. The agent respects it.
✓
Binds to 0.0.0.0 — required for Cloud Run's load balancer to reach the container.
✓
Health-check endpoint — /.well-known/agent.json returns 200. Cloud Run startup and liveness probes will use this.
✓
Stateless — in-memory task store, no local disk dependencies. Scales to zero safely.
⚠
Secrets in env vars — currently read from environment. We'll move them to Secret Manager in Lab 4.

Containerize the Agent

Write a production Dockerfile and test it locally before pushing to the cloud.

1

Write the Dockerfile

Create Dockerfile in the ar-email-agent/ directory:

# ── Stage 1: build dependencies ──────────────────────────
FROM python:3.12-slim AS deps

WORKDIR /build

# Install only what's needed to compile wheels
RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential gcc \
  && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ── Stage 2: runtime image ──────────────────────────────
FROM python:3.12-slim AS runtime

WORKDIR /app

# Copy compiled packages from build stage
COPY --from=deps /install /usr/local

# Copy application source
COPY app/ .

# Non-root user for security
RUN useradd -m -u 1000 agent
USER agent

# Cloud Run injects PORT at runtime — default to 8080
ENV PORT=8080 \
    HOST=0.0.0.0 \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

EXPOSE 8080

CMD ["python", "main.py"]
Why multi-stage? The final image has no gcc or build tools — only the runtime. Typical result: 900 MB → 180 MB. Smaller images = faster cold starts.
2

Add .dockerignore

Keep secrets and local state out of the image:

__pycache__/
*.pyc
*.pyo
.env
.env.*
*.local
.git/
.gitignore
*.md
tests/
.pytest_cache/
3

Build and test locally

# Build
docker build -t ar-email-agent:local .

# Run with mock data — same flag as local Python
docker run -p 8080:8080 \
  -e IBD_TESTING=1 \
  ar-email-agent:local

# Verify health check responds
curl http://localhost:8080/.well-known/agent.json
You should see the agent card JSON. If you see Connection refused, the container exited — run docker logs $(docker ps -lq) to debug.
4

Inspect image size

docker image inspect ar-email-agent:local \
  --format='{{.Size}}' | numfmt --to=iec

Target: under 250 MB. If it's larger, check whether large model weights are being copied into the image by mistake.

Common gotcha: If your agent loads model weights locally (e.g. from a models/ folder), do NOT copy them into the image. Cloud Run agents should call remote LLM APIs — never bundle weights.

Deploy to Cloud Run

Push the image and get a public HTTPS URL for your agent in under 5 minutes.

1

Deploy with one command

--source . triggers Cloud Build to build the image for you — no separate docker push needed.

gcloud run deploy ar-email-agent \
  --source . \
  --region $REGION \
  --allow-unauthenticated \
  --port 8080 \
  --set-env-vars IBD_TESTING=1 \
  --service-account ar-email-agent-sa@$PROJECT_ID.iam.gserviceaccount.com

Build takes ~2 minutes on first run. Subsequent deployments are faster (layer cache).

2

Get the service URL and test

export SERVICE_URL=$(gcloud run services describe ar-email-agent \
  --region $REGION \
  --format='value(status.url)')

echo "Agent live at: $SERVICE_URL"

# Health check
curl $SERVICE_URL/.well-known/agent.json | python3 -m json.tool

# Send a message
curl -X POST $SERVICE_URL/ \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"tasks/send","id":1,
       "params":{"message":{"role":"user","parts":
       [{"type":"text","text":"Show all overdue customers"}]}}}'
3

View real-time logs

gcloud run services logs tail ar-email-agent \
  --region $REGION

You should see agent log lines appear as you send requests. We'll improve this in Lab 6.

4

Inspect the service in the Console

Open Cloud Console → Cloud Run → ar-email-agent. Note:

  • The container URL matches $SERVICE_URL
  • The Revisions tab shows ar-email-agent-00001-xxx with 100% traffic
  • Metrics shows request count, latency, and instance count
🎉 Your agent is now live on the internet with a TLS-terminated HTTPS URL, auto-scaled to zero when idle. That's Cloud Run's default — you pay nothing when there are no requests.

Secrets & Configuration

Never put credentials in environment variables or Docker images. Use Secret Manager.

Never do this: --set-env-vars SMTP_PASSWORD=hunter2
Env vars are visible in the Cloud Console, build logs, and gcloud run services describe. Treat them as public.
1

Create a dedicated service account

gcloud iam service-accounts create ar-email-agent-sa \
  --display-name="AR Email Agent"

export SA_EMAIL=ar-email-agent-sa@$PROJECT_ID.iam.gserviceaccount.com

Principle of least privilege: this SA gets only the permissions the agent actually needs, nothing more.

2

Store credentials in Secret Manager

# SMTP credentials for email sending
echo -n "your-smtp-user@gmail.com" | \
  gcloud secrets create smtp-user --data-file=- --replication-policy=automatic

echo -n "your-app-password-here" | \
  gcloud secrets create smtp-password --data-file=- --replication-policy=automatic

# Verify
gcloud secrets list
3

Grant Secret Manager access to the service account

for secret in smtp-user smtp-password; do
  gcloud secrets add-iam-policy-binding $secret \
    --member="serviceAccount:$SA_EMAIL" \
    --role="roles/secretmanager.secretAccessor"
done
4

Redeploy with secrets bound

Cloud Run fetches secrets at container startup and injects them as env vars. The values never appear in config.

gcloud run deploy ar-email-agent \
  --source . \
  --region $REGION \
  --service-account $SA_EMAIL \
  --set-secrets SMTP_USER=smtp-user:latest,SMTP_PASSWORD=smtp-password:latest \
  --set-env-vars IBD_TESTING=1,SMTP_HOST=smtp.gmail.com,SMTP_PORT=465
5

Rotate a secret without redeploying

Add a new version. The next container startup picks it up automatically (because you used :latest).

echo -n "new-password-here" | \
  gcloud secrets versions add smtp-password --data-file=-

# Force a new revision to pick it up immediately
gcloud run services update ar-email-agent \
  --region $REGION \
  --description "Updated SMTP credentials"

Production Hardening

Configure health probes, resource limits, and scaling to handle real traffic.

Part A: Health probes

Tell Cloud Run exactly when your container is ready — and when to restart it.

The three probe types:
• Startup — allows extra time for slow-starting containers. Checked only during cold start.
• Liveness — kills and replaces the container if it becomes unhealthy.
• Readiness — temporarily removes the container from the load balancer without killing it. 
# service.yaml — deploy-as-config approach for precise probe control
apiVersion: serving.knative.dev/v1
kind: Service
metadata:
  name: ar-email-agent
spec:
  template:
    spec:
      serviceAccountName: ar-email-agent-sa@PROJECT_ID.iam.gserviceaccount.com
      containers:
      - image: gcr.io/PROJECT_ID/ar-email-agent
        ports:
        - containerPort: 8080
        resources:
          limits:
            cpu: "1"
            memory: 512Mi
        startupProbe:
          httpGet:
            path: /.well-known/agent.json
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 5
          timeoutSeconds: 3
          failureThreshold: 18    # 90s total startup window
        livenessProbe:
          httpGet:
            path: /.well-known/agent.json
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 10
          timeoutSeconds: 5
          failureThreshold: 3
# Deploy from YAML (replace PROJECT_ID first)
sed -i "s/PROJECT_ID/$PROJECT_ID/g" service.yaml
gcloud run services replace service.yaml --region $REGION

Part B: Scaling configuration

AI agents are usually not high-throughput — tune accordingly.

gcloud run services update ar-email-agent \
  --region $REGION \
  --min-instances 0 \     # scale to zero when idle (saves cost)
  --max-instances 5 \     # cap concurrent instances
  --concurrency 4 \       # LLM calls are blocking — keep this low
  --timeout 120           # agents can be slow; default 60s is often too short
Why concurrency=4 for LLM agents? Each request holds a live LLM connection while streaming. High concurrency causes context-switching overhead with no throughput benefit. Unlike stateless web handlers, AI agents are CPU-bound for token generation — keep concurrency low.

Part C: CPU throttling vs. always-on

CPU Throttled (default)
CPU allocated only during request handling. Background tasks, cleanup code, and timers don't run between requests.
Best for: stateless agents, cost-sensitive workloads
CPU Always-On
CPU allocated at all times when at least one instance is running. Needed for background threads, polling, scheduled cleanup.
Enable: --no-cpu-throttling

Part D: Eliminate cold starts

If cold starts are unacceptable (e.g. user-facing agents), set a minimum of 1 always-warm instance:

gcloud run services update ar-email-agent \
  --region $REGION \
  --min-instances 1 \
  --startup-cpu-boost    # extra vCPU during startup only (faster init)

Cost: ~$5/month per always-warm instance (e2-micro equivalent). Usually worth it for production agents.

Observability

Structured logs, distributed traces, and dashboards so you actually know what your agent is doing in production.

Part A: Structured JSON logging

Cloud Logging understands structured JSON natively. Add this formatter to app/main.py:

import json, logging, sys

class CloudRunFormatter(logging.Formatter):
    def format(self, record):
        entry = {
            "severity": record.levelname,
            "message": record.getMessage(),
            "logger": record.name,
        }
        # Forward OpenTelemetry trace context if available
        span = trace.get_current_span()
        ctx = span.get_span_context()
        if ctx.is_valid:
            entry["logging.googleapis.com/trace"] = \
                f"projects/{PROJECT_ID}/traces/{ctx.trace_id:032x}"
            entry["logging.googleapis.com/spanId"] = f"{ctx.span_id:016x}"
        return json.dumps(entry)

handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(CloudRunFormatter())
logging.root.addHandler(handler)
logging.root.setLevel(logging.INFO)
The logging.googleapis.com/trace field links log lines to their distributed trace in Cloud Trace. You can click a log entry and jump directly to the span that produced it.

Part B: OpenTelemetry traces to Cloud Trace

Add to requirements.txt:

opentelemetry-sdk
opentelemetry-api
opentelemetry-exporter-gcp-trace
opentelemetry-instrumentation-fastapi

Bootstrap telemetry in main.py (before other imports):

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.cloud_trace import CloudTraceSpanExporter

provider = TracerProvider()
provider.add_span_processor(
    BatchSpanProcessor(CloudTraceSpanExporter())
)
trace.set_tracer_provider(provider)

Wrap agent tool calls in spans for visibility:

tracer = trace.get_tracer(__name__)

# In agent_executor.py, wrap tool execution:
with tracer.start_as_current_span("agent.execute",
    attributes={"query": query, "task_id": task.id}):
    async for item in self.agent.stream(query, ...):
        ...

Scaling & Safe Rollouts

Deploy a new revision without downtime using traffic splitting.

Part A: Deploy a new revision with no traffic

# Deploy v2 — send 0% traffic to it initially
gcloud run deploy ar-email-agent \
  --source . \
  --region $REGION \
  --no-traffic \
  --tag canary

# Get the canary URL (tagged revisions get a dedicated URL)
gcloud run services describe ar-email-agent \
  --region $REGION \
  --format='value(status.traffic)'

With --tag canary, Cloud Run gives the new revision its own URL: https://canary---ar-email-agent-xxx.run.app. Test it directly without affecting live users.

Part B: Gradually shift traffic

# Get revision names
gcloud run revisions list --service ar-email-agent --region $REGION

# 10% canary, 90% stable
gcloud run services update-traffic ar-email-agent \
  --region $REGION \
  --to-tags canary=10

# Watch metrics split in Cloud Monitoring, then promote to 100%
gcloud run services update-traffic ar-email-agent \
  --region $REGION \
  --to-latest

Part C: Instant rollback

If something goes wrong, roll back to the previous stable revision in seconds:

# List revisions to find the stable one
gcloud run revisions list --service ar-email-agent \
  --region $REGION --format='table(name,status.conditions[0].type)'

# Roll back immediately — all traffic to the stable revision
gcloud run services update-traffic ar-email-agent \
  --region $REGION \
  --to-revisions ar-email-agent-00001-xxx=100
Cloud Run keeps every revision you've deployed. Rollbacks are instant — it's just a traffic pointer change, not a redeploy.

Part D: Quick load test

Watch Cloud Run auto-scale in real time:

# Install hey (HTTP load tester)
brew install hey   # or: go install github.com/rakyll/hey@latest

# 50 concurrent requests for 30 seconds
hey -c 50 -z 30s $SERVICE_URL/.well-known/agent.json

Open Cloud Console → Cloud Run → ar-email-agent → Metrics and watch instance count rise, then fall back to minimum after the test ends.

🎉 Congratulations — you have a production-ready, observable, auto-scaling AI agent on Cloud Run.
