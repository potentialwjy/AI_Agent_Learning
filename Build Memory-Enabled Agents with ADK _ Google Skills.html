    Overview

    You know these five sentences. Everyone knows these five sentences:

    1. "What was your order number again?"
    2. "You've been transferred. Please describe your issue from the beginning."
    3. "Welcome! How can I help you today? 😊" — said to a customer with an open ticket from last month
    4. "Could you describe the damage?" — after you already sent a photo
    5. "Hmm, we've never seen this issue." — while 37 tickets on the same batch sit in the system

    Every one of them is a memory failure — a specific, nameable gap in how the system remembers. And "memory" is not one thing: re-asking within a chat, losing a conversation at handoff, forgetting a returning customer, dropping an uploaded photo, and missing what the whole company already knows are five different gaps, each with its own mechanism.

    Short-term memory is given to you by the framework; every long-term layer is a write policy plus a recall policy that you choose. This lab climbs those layers one at a time.

    You play the support lead at Lumen & Co., a smart-lamp company. Your agent is Iris. Your customer is Maya, and her LumenGlow v2 flickers.

    Iris — the support agent you're fixing Maya — the customer holding a cracked lamp

    Iris starts the lab with all five failures in place — mechanically, because the code for remembering isn't written yet. You will write it. Every task repeats the same loop: run the broken behavior and watch it with your own eyes → open the file (cloudshell edit) → delete a # TODO: prefix so the one line that is the whole lesson goes live → relaunch adk web → same prompts, different world.

    What you'll learn

    • tool_context.state — the channel your code reads, next to the transcript the model reads
    • LongRunningFunctionTool and FunctionResponse — parking a run for a human, and answering it from another process
    • add_session_to_memory / search_memory — a write policy and a recall policy, named and written by you
    • Connecting Vertex AI Memory Bank on an Agent Engine instance you deploy yourself
    • save_artifact — giving an upload a home, and extracting facts from it into state
    • Governed traversals and semantic search over BigQuery, with embeddings generated in place
    Tip: 📦 All the code is on GitHub: github.com/cuppibla/support-memory-lab — you'll clone it in Task 1. Every rung is a folder; the finished versions live in _solutions/ if you get stuck.

    Task 2. State — "What was your order number again?"

    Two channels inside one conversation: the transcript the model reads, and the state your code trusts.

    • The failure — nothing Maya says becomes anything your code can use.
    • The line you'll write — the state write, the single line that separates a chat from a system.

    Write the line that makes state real

    Before you run anything, the line this whole task is about is switched off.

    👉💻 Open the file:

    cloudshell edit ~/support-memory-lab/r1_short_term/tools.py

    👀 Read update_ticket. It computes the key, builds the response… and the one line that would store anything is commented out:

    key = f"ticket_{field}" # ── YOUR LINE ─ delete the "# TODO: " prefix ────────────────────────── # TODO: tool_context.state[key] = value return {"status": "success", "written": {key: value}}

    👉📝 Your line: delete the # TODO: prefix so it reads tool_context.state[key] = value. Writing through the tool context makes ADK record the change as part of the event, so it lands on disk with everything else.

    Tip: Why one commented line is the whole task. Leave it off and nothing looks broken: the tool still returns {"status": "success"}, and Iris still answers follow-up questions correctly — from the transcript, because within a single session the model can read the raw history back. That is exactly what makes this bug invisible in a demo and fatal in production. The model remembers prose; your code — the part that files tickets, issues refunds, routes escalations — has no field to read and no value to act on. State is the second channel, and it exists only because you wrote that line.

    Launch adk web

    👉💻 This is the command you'll use all lab long. Read the flags before you run them — two of them ARE the curriculum:

    cd ~/support-memory-lab source .venv/bin/activate PYTHONPATH=$PWD adk web . --allow_origins="*" \ --session_service_uri "sqlite:///lumen.db" \ --artifact_service_uri "file://$PWD/artifacts_store"
    • --session_service_uri "sqlite:///lumen.db" — this constructs a SessionService, the ADK component that decides WHERE conversations live: sqlite:// builds a SqliteSessionService over a real file (the family also includes DatabaseSessionService for Postgres/Cloud SQL and VertexAiSessionService for managed sessions). This task ends by flipping this flag; Task 3 exists because of it.
    • --artifact_service_uri "file://$PWD/artifacts_store" — uploaded files get a real directory. Task 7's whole plot.
    • --allow_origins="*" — not optional in Cloud Shell: Web Preview proxies you through an https://8000-…cloudshell.dev origin the server would otherwise reject, and the UI fails in confusing ways (an empty agent list is the classic symptom).

    Behind these flags, adk web builds a Runner for each agent folder — ADK's engine, whose one job is run_async(user_id, session_id, new_message): run the agent one turn against the wired services. You'll open a Runner you can actually read in Task 4.

    👉🌐 Open it via Web Preview → Change port → 8000 (the Web Preview button sits top-right of the Cloud Shell toolbar). The ADK dev UI opens — you'll learn its parts as you need them.

    Bookmark this one — you'll relaunch this command a dozen times. If it ever refuses to start with
    [Errno 98] error while attempting to bind on address ('127.0.0.1', 8000): address already in use

    an earlier adk web is still holding port 8000. Almost always because a terminal tab got closed instead of stopped with Ctrl-C, which leaves the server running with nothing attached to it. 👉💻 Free the port and try again: pkill -f "adk web" Nothing is lost when you do that — every conversation is in lumen.db, which is the whole point of Task 2.     Task 3. The handoff — "Please describe your issue from the beginning."

    Only one dial moved. Persistence changes where the conversation lives — not what kind of memory it is.

    • The failure — escalation exists, but no human is actually in the loop; the run never stops to wait for one.
    • The lines you'll write — the LongRunningFunctionTool wrapper, and the FunctionResponse a supervisor sends back.

    First, run it broken

    👉💻 Make sure adk web is running — if you stopped it, relaunch:

    cd ~/support-memory-lab source .venv/bin/activate PYTHONPATH=$PWD adk web . --allow_origins="*" \ --session_service_uri "sqlite:///lumen.db" \ --artifact_service_uri "file://$PWD/artifacts_store"

    👉🌐 Open it via Web Preview → Change port → 8000. Pick r2_handoff from the agent dropdown and send:

    This replacement lamp is broken too. I want an $80 refund for order 8841.

    👀 Watch the escalate_refund chip: it goes ⚡→✓ instantly, inside the same turn, and Iris keeps talking — most likely speaking as if a review happened.

    👉🌐 Click the ✓ escalate_refund chip to open its event detail and read the response JSON. The tool returned:

    {"status": "pending", "reason": "Replacement lamp is broken.", "amount": 80}

    "status": "pending" — and the model just kept going. Read those two things together, because that is the whole bug: the tool itself said the work was not finished, and the turn rolled straight past it.

    Nothing stopped it. An ordinary tool returns and the turn rolls on — "pending" was just a word in a dict. Nothing in the runtime treats it as stop and wait: no approval step happened, and nothing is waiting for one. Whatever Iris told Maya about a supervisor, there is no parked call anywhere for a human to find.

    Remember what this chip looks like. After you fix this, the chip will still go ⚡→✓ and the response will still say "status": "pending" — that part never changes, and it is not how you'll tell the fix worked. What changes is whether anything is waiting. We'll point at the exact tell.

    Fix half one: park the run

    👉💻 Press Ctrl-C in the adk web terminal, then open the file:

    cloudshell edit ~/support-memory-lab/r2_handoff/agent.py # TODO: from google.adk.tools import LongRunningFunctionTool … escalation = escalate_refund # TODO: escalation = LongRunningFunctionTool(escalate_refund) root_agent = make_iris([update_ticket, escalation])

    👉📝 Your two lines: delete both # TODO: prefixes — the import at the top, and the wrap. A long-running tool tells ADK: "what this function just returned is not the final answer — the real one arrives later, from outside." ADK records the call id as unanswered so a second process can find it and reply. Note what it does not do: it doesn't stop the function running, and it doesn't hide the "pending" dict from the model. Iris still gets it, and still uses it to tell Maya a human is looking.

    👉💻 Relaunch the server:

    cd ~/support-memory-lab source .venv/bin/activate PYTHONPATH=$PWD adk web . --allow_origins="*" \ --session_service_uri "sqlite:///lumen.db" \ --artifact_service_uri "file://$PWD/artifacts_store"

    👉🌐 Reload the Web Preview tab (it opens a fresh session), pick r2_handoff from the agent dropdown again, and send the exact same refund message as before — copy and paste it:

    This replacement lamp is broken too. I want an $80 refund for order 8841.

    👀 First, the thing that did not change. The escalate_refund chip still goes ⚡→✓, and clicking it still shows "status": "pending". Iris still says a supervisor is reviewing. If you were looking for the pending to disappear: it doesn't, and that is correct. A long-running tool still runs, still returns immediately, and its return value is still handed to the model — that is how Iris knows to tell Maya a human is looking at it. LongRunningFunctionTool was never a promise to change the chip.

    👀 Now the tell. Look between the ⚡ row and the ✓ row: there is a new Enter your response... input box with a send arrow, sitting inside the event feed — highlighted in amber below. That box is the dev UI saying this call is parked and I am holding it open for an answer from outside. It did not exist on your broken run. In the graph below, escalate_refund is also drawn with a heavier dashed outline than update_ticket — the UI's marker for a long-running tool.

    That box is a fully working supervisor console. Whatever you type becomes the tool's real return value: paste valid JSON and it is sent as-is, type bare text and it is wrapped as {"result": "your text"}.

    So the turn ends — same as before — but this time something is waiting. That is the difference the chip could never have shown you.

    Fix half two: answer the parked call

    👉🌐 Click into the Enter your response... box, paste the supervisor's decision, and press the send arrow:

    {"status": "approved", "approved_by": "supervisor", "note": "Refund approved. Tell the customer it arrives in 3-5 days."}

    Read it like a sentence before you send it. status is what the tool finally "returns"; the rest is context the model can quote back. This is the FunctionResponse the runtime has been holding the turn open for — the answer that arrived later, from outside.

    👀 The run resumes on the spot. A new ✓ escalate_refund chip appears carrying your response, and Iris picks the conversation back up:

    IRIS: ...it has been approved! You should see that $80 refund in 3-5 business days.

    Maya never repeated a word. The turn stopped for a human and started again the moment the human answered — and the conversation it resumed was read back out of lumen.db, not held in the model's head.

    A parked call can be answered exactly once. Once you send that response the escalation is closed and the box disappears. If you want to watch it again, or try a denial instead, send the refund message once more to park a fresh call:
    This replacement lamp is broken too. I want an $80 refund for order 8841.

    No response box to type into? Then nothing is parked, and the wrap is the reason — check `r2_handoff/agent.py` reads escalation = LongRunningFunctionTool(escalate_refund) with the import above it uncommented, relaunch, and send the refund message again. An ordinary tool leaves nothing behind for anyone to answer; parking is what creates the supervisor's job in the first place.     Tip: The beat: a human can only "check the chat history" if the history lives outside the process. Persistence isn't a durability feature that happens to sit near human-in-the-loop — it's the precondition for it.

    Want to see that literally? The repo ships r2_handoff/supervisor.py — seventy lines that open the same lumen.db with the same SqliteSessionService adk web is using, scan for an unanswered escalate_refund, print the history a human would review, and send back exactly the FunctionResponse you just pasted. 👉💻 cloudshell edit ~/support-memory-lab/r2_handoff/supervisor.py — worth reading even if you never run it.     Task 5. Long-term memory — "Welcome! How can I help you today?"

    A new kind of memory — but still inside the process, so it dies with the server. The next task fixes that.

    • The failure — Maya returns a week later and Iris treats her as a stranger, while last week's session sits in the same database.
    • The lines you'll write — the write policy and the recall policy.

    After Task 3 you might believe: "my sessions are in SQLite, so my agent has memory." This task breaks that belief. Persistence answers can this conversation survive? Memory answers can the NEXT conversation use it? Different questions, different machinery.

    Run it broken

    👉💻 Make sure adk web is running — if you stopped it, relaunch:

    cd ~/support-memory-lab source .venv/bin/activate PYTHONPATH=$PWD adk web . --allow_origins="*" \ --session_service_uri "sqlite:///lumen.db" \ --artifact_service_uri "file://$PWD/artifacts_store"

    Write both policies

    👉💻 Press Ctrl-C in the adk web terminal, then open the file:

    cloudshell edit ~/support-memory-lab/r3_last_month/tools.py

    Read more: how those vectors got there

    The script did this part, so nothing below is a step — but the three mechanisms are the reason the warehouse can answer a question no keyword matches, and they're worth the ninety seconds.

    👀 A connection is an identity. bq mk --connection --connection_type=CLOUD_RESOURCE creates a service account named bqcx-…@gcp-sa-bigquery-condel.iam.gserviceaccount.com, born with the connection and holding no permissions at all. BigQuery uses it to call Vertex on your behalf, so it has to be granted that right:

    gcloud projects add-iam-policy-binding "$PROJECT" \ --member="serviceAccount:$CONN_SA" --role=roles/aiplatform.user --condition=None

    👀 A remote model is a handle, not a copy. Nothing is downloaded. The model is a name in your dataset pointing at a Vertex endpoint through that connection:

    CREATE OR REPLACE MODEL lumen.embedder REMOTE WITH CONNECTION `us-west1.vertex_conn` OPTIONS (ENDPOINT = "gemini-embedding-001")

    👀 The embeddings never left the warehouse. With that handle in place, one statement turns forty ticket rows into forty vectors in the same dataset — no export, no pipeline, no separate vector database:

    CREATE OR REPLACE TABLE lumen.ticket_embeddings AS SELECT id, content, ml_generate_embedding_result AS embedding FROM ML.GENERATE_EMBEDDING(MODEL lumen.embedder, (SELECT id, text AS content FROM lumen.tickets))

    That is the whole "in place" claim: ML.GENERATE_EMBEDDING called Vertex from inside BigQuery and wrote the results back beside the rows they came from. A vector here is just a list of 3072 numbers describing what a sentence means, so two tickets land near each other when they describe the same problem in different words — which is exactly what InMemoryMemoryService could not do back in Task 5, where it scored memories by counting shared words.

    👉🌐 See it: in BigQuery Studio, Explorer pane → your project → lumen → ticket_embeddings. Schema shows embedding as a REPEATED FLOAT; Details puts the row count at 40. Your tickets and their vectors are one table, sitting in the same dataset as customers and orders.

    Tip: Why the script retries CREATE MODEL. It is the first statement that actually exercises the IAM grant, and IAM is eventually consistent — so for a minute or so after a grant that worked perfectly it fails with does not have the permission to access or use the endpoint, naming the bqcx-… account and asking for the Agent Platform User role.

    That role is not missing. "Agent Platform User" is just the current display name of roles/aiplatform.user, renamed when Vertex AI moved under the Gemini Enterprise Agent Platform branding — same role ID, already granted. The script polls through the propagation window instead of handing you that error. If it ever does stop there, re-running it is safe.
