Chapter 1 · 你的第一个 Agent

最小可用的 Agent 长什么样，没有工具意味着什么

这章学什么：读懂世界上最小的 Agent（只有4行），然后亲眼看到"没有工具的 Agent 只是一段被认真交代过任务的对话"。
要做的事：启动 adk web，发两句话，看 State 标签页。不需要改代码。

启动 Dev UI

cd ~/agent-valley-lab
uv run adk web . --allow_origins="*"

通过 Web Preview → Change port → 8000 打开界面，选择 grove（不是 grove_locked）。

⚠️ 为什么必须加 --allow_origins="*"？
Cloud Shell Web Preview 会用一个 https://8000-cs-....cloudshell.dev 形式的域名代理你的请求，这个域名和 ADK Dev UI 内部认为自己在的地址 http://127.0.0.1:8000 不一致。ADK 会对每个 POST 请求做 CORS 检查——不加这个参数，界面能加载，但你发第一条消息就会收到 403 Forbidden。

读懂这个 Agent

打开 grove/agent.py，忽略注释，有效的代码只有这4行：

root_agent = LlmAgent(
    name="grove",
    model="gemini-3-flash-preview",
    instruction=INSTRUCTION,
)
参数作用
nameDev UI 里显示的名字
model背后用哪个 AI 大脑（这里是 Gemini 3 Flash）
instruction它的"工作说明书"——告诉它自己是谁、能做什么。向上滚动查看 INSTRUCTION：7句话描述了"我是一个保管着魔法熔炉的人，旅行者描述什么我就召唤什么可爱动物"

注意：没有 tools 参数。这是这一章最关键的事实。

动手试验

在 Dev UI 里输入：

Summon a fox familiar for me.

你会收到一段美丽的文字描述——可能是一只穿着毛衣、捧着茶杯的青蛙。然后再问：

Show me it.

你得到的依然是文字。没有图片，没有文件，没有任何真实存在的东西被创造出来。

点击 State 标签页——它是空的。

这一章的结论

核心认知

模型的唯一输出通道是文字。"它说它做了某件事"和"它真的做了这件事"，从文字上看起来完全一样。这不是 bug，不是坏模型——这是模型的本质限制。

没有工具的 Agent，是一段被认真交代过任务的对话，仅此而已。

Chapter 2 · 你的第一个工具

给 Agent 加上一个函数，然后跟踪数据的完整流向

这章学什么：一行改动，Agent 从"只会说"变成"真的做"。重点是理解模型、runtime、工具三者之间的分工，以及图片到底是哪来的。
要做的事：删掉一个 # 符号，重启 Dev UI，追踪调用链。

唯一的代码改动

打开 grove/agent.py，找到这一行，删掉行首的 # ：

root_agent = LlmAgent(
    name="grove",
    model="gemini-3-flash-preview",
    instruction=INSTRUCTION,

    # 删掉下面这行的 "# "，然后保存
    tools=[cast_candidates],
)

保存，然后重启 Dev UI（Ctrl+C 后重新运行 uv run adk web . --allow_origins="*"）。

再次发送同样的请求

something cozy that likes rain and drinks tea

这次完全不同：出现一个 cast_candidates 调用气泡，停顿约 12 秒，然后弹出一张真实存在的图片。

关键问题：工具调用的本质是什么？

点开那个 cast_candidates 气泡，你会看到 4 条消息。把它们拆开：

步骤谁做的做了什么
1你发了一句话："something cozy that likes rain…"
2模型（LLM）输出一条消息，说"我要调用 cast_candidates，参数是这段视觉描述"——把你的几个词扩写成完整描述
3Runtime（ADK 框架）读到模型的输出，真正调用 Python 函数，等待返回
4模型收到函数的返回值，生成最终回复
🔑 最重要的认知
第2步里，模型的输出仍然只是一条文字消息。它做的是"决定调用什么、写好参数"，但它自己什么都没执行。真正让函数跑起来的是 ADK Runtime（第3步）。

模型负责"决定 + 组织语言"，Runtime 负责"真正执行"。这两者是分开的。

函数的"契约"——docstring 是给模型看的

打开 forge/agent/tools.py，找到 cast_candidates：

async def cast_candidates(description: str, tool_context: ToolContext) -> dict:
    """Draw the familiar a traveler described.

    Args:
        description: What the creature looks like — species, colours, mood, era.
    """

模型能看到的关于这个函数的信息，只有三样：函数名、参数签名、docstring。没有函数体，没有实现细节。这就是为什么要用清晰的大白话写 docstring——你是在给一个"读者"（模型）写说明书，不是在给编译器写注释。写得含糊，模型调用时就会出错或乱猜参数。

图片从哪来的？——完整调用链

这是大多数教程会跳过的部分：

  1. grove 本身不会画画。它是纯文本模型（gemini-3-flash-preview），文字进、文字出。
  2. 真正画图的是另一个模型。在 cast_candidates 函数内部，调用了 gemini-2.5-flash-image——一个专门的图像生成模型，和 grove 完全独立。
  3. 画风是靠"喂图片"实现的。打开 forge/agent/backends.py，找 _style_refs()：每次请求都附带 4 张示例图作为美术风格的锚点，这是纯文字提示词很难达到的效果。
  4. 模型自己从未看到生成的图片。图片字节被 save_artifact() 存起来，回传给 grove 的只是一个字符串 "candidate_0.png"——小到能塞进一个 prompt 里。
grove
文本模型 → cast_candidates()
Python 函数 → gemini-2.5-flash-image
图像生成模型
grove 没有变成多模态——它只是拿到了一扇通往图像模型的门

为什么用两个独立模型？

  • 可以单独替换"画图的部分"，而不用动"思考的部分"
  • 只有真正调用画图的那一步才计图像生成的费用
  • 两个模型可以独立更新、独立优化

三件事，边玩边观察

观察 1

你打的每一句话，走的还是你在第4章读过的那套代码——同样的 cast_candidates 函数，同样的 docstring。

观察 2：建议是"写词"，不是"按按钮"

按钮本身没有"意图"——模型从一个按钮点击里什么都读不出来。一句完整的话才携带意图，这是模型能参与这个循环的唯一理由。

观察 3

山谷本身完全不依赖你之前的代码编辑——它有自己的 Agent（forge/agent/lanes.py），从一开始就能独立运行。

悬念一：右侧追踪面板里的日志

发送一个装扮请求时，右侧面板会出现类似这样的内容：

after_model    guard: pass
before_tool    identity lock → candidate_0.png
after_tool     + a golden crown  ·  outfit: a golden crown

一句话触发了 6 行日志。有东西在悄悄写状态，有东西在帮你选图片——这是什么？数据写到哪里去了？

→ 答案在第6章（共享的 state 字典）

悬念二：脸为什么没有变？

你连续加了皇冠、披风、灯笼……但你的生物脸从未变过，哪怕你从没重新描述过它本身。是什么东西替你"记住"了原始形象？能不能关掉这个机制？

你加了 4 件装扮，OUTFIT 计数是 4，脸还是原来的脸
第1次：原始形象 → 加皇冠 → 加披风 → 加灯笼
每次都是"同一张脸 + 新装扮"，不是"上一次的图 + 新装扮"——但为什么？

每件装扮旁边都有一个 ✕ 按钮。移除这个操作没有歧义，不需要模型来"理解"，直接执行就行——正好和"建议只写词、不按按钮"是镜像的道理。

Chapter 4 · 第二个工具——两个工具如何"对话"

工具之间不互相调用，靠一个共享字典传数据——理解这个，能省你几周调试时间

这章学什么：加第二个工具，然后弄清楚两个工具是怎么互相"认识"对方的工作成果的。关键答案是 tool_context.state——一个共享字典。
要做的事：往 tools 列表加一个名字，重启 Dev UI，观察 State 标签页。

唯一的代码改动（Lab 的最后一次编辑）

打开 grove/agent.py，在 tools 列表里加一个名字：

tools=[cast_candidates, lock_candidate],

加工具就是"往列表里加个名字"——这是整个 Lab 的最后一次代码改动。

一句话触发两个工具

重启 Dev UI，新建会话，发送：

summon something cozy that likes rain, and call it Mochi

你会看到两个调用气泡依次出现：先 cast_candidates，再 lock_candidate。

核心问题：lock_candidate 怎么知道要锁定哪张图？

打开 lock_candidate 的调用记录，模型实际传入的参数是：

lock_candidate(index=0, name="Mochi")

看它的函数签名（在 forge/agent/tools.py）：

async def lock_candidate(index: int, name: str, tool_context: ToolContext) -> dict:
    """Lock one candidate as the canonical character."""
    candidates = tool_context.state.get("temp:candidates", [])
    ref = candidates[index]
    tool_context.state["character_ref"] = ref

参数里没有文件名，没有图片，没有列表。模型能给它的只有一个数字和一个名字。那文件名从哪来的？

🔑 答案：tool_context.state——共享字典
两个工具函数从来不互相调用。是 tool_context.state 这个字典在中间做"手递手"。

cast_candidates 把候选文件名列表写进 state["temp:candidates"]；lock_candidate 运行时，从这个字典里按 index=0 取出对应文件名。

没有消息传递，没有返回值通道——就是一个共享的"房间"，一个写进去，下一个读出来。

cast_candidates 写了什么进 state？

查看 forge/agent/tools.py 中 cast_candidates 的最后几行：

tool_context.state["temp:candidates"] = filenames       # 候选图文件名列表
tool_context.state["character_sheet"] = {"name": "", "description": description}
tool_context.state["provisional_ref"] = filenames[0]   # 临时参考图（还没命名）
tool_context.state["temp:provisional_ref_png"] = pngs[0][0]  # 图片字节（临时）

State 标签页里的完整记录

两个工具都跑完后，点 State 标签页：

character_sheet   {"name": "Mochi", "description": "A cozy red panda...", "style_notes": ""}
provisional_ref   ""
character_ref     "candidate_0.png"
look_history      []
字段谁写的含义
character_sheetcast_candidates（名字为空）→ lock_candidate（填入 Mochi）角色档案
provisional_refcast_candidates 写入 → lock_candidate 清空为 ""临时参考图，锁定后被清空
character_reflock_candidate正式的、被认领的参考图

那个空字符串（provisional_ref = ""）是这章的精华：cast_candidates 之后只有"参考"，lock_candidate 之后才有"角色"。清空就是跨越的"收据"。

Agent 也读这个字典

打开 forge/agent/character_forge.py，看它的 instruction 模板：

Character card: {character_sheet?}

ADK 在每次调用模型之前，会自动把 state 里对应的值填进去。工具写了 character_sheet，prompt 把它读回来给模型——一次完整的闭环，而且工具文件、Agent 文件、state 三者之间没有任何 import 关系。

两条必须记住的规则

规则 1：大东西不进 state

1.3MB 的图片去 artifacts（附件系统），只有文件名字符串进 state。因为每次给模型的 prompt 是纯文字，任何要让模型看到的东西都必须能塞进一段文字里。

规则 2：前缀决定寿命
前缀存活时间
temp:只活一个回合（turn），下一条消息就消失
无前缀整个对话 session
user:跨 session 永久保存
⚠️ 动手验证 temp: 规则
新建会话，把请求拆成两轮：第1轮 summon something cozy，第2轮 claim the first one and call it Mochi。第2轮会报错 index 0 out of range——因为 temp:candidates 已经因为 turn 结束而消失了。这就是为什么 State 标签里看不到 temp: 前缀的键，它们从不被持久化。

这章的核心结论

核心认知

一个工具真正的输出，不是它嘴上说的那句总结性的话，而是它写进 state 里的东西。

模型没有在两个工具之间传数据——一个字典做到了。

Chapter 5 · Callback——伸手进那根线里

解答"为什么脸没变"；理解指令、点击、Callback 三种控制力度的本质区别

这章学什么：什么是 Callback，在哪个时刻触发，用来做什么。重点是理解 before_tool 如何在模型开口之前悄悄把原始图片塞进去，以及"打开/关闭 identity lock"对图片漂移的影响。
要做的事：读代码（不需要改），对比 grove 和 grove_locked 的行为，在 valley 里开关 identity lock。

什么是 Callback？

Callback 是你自己的普通函数，在 ADK 框架里被挂载到五个固定的时刻，ADK 保证每次到了那个时刻就会自动调用它——不管模型愿不愿意，每次必然执行。

打开 forge/agent/callbacks.py，看到5个函数：

函数名触发时刻
before_model发送给模型之前
after_model模型返回之后
before_tool模型决定调用工具之后、函数真正执行之前（能改变工具收到什么）
after_tool工具函数执行完毕之后
on_end整个回合结束时
💡 谁在调用 Callback？
在 forge/agent/character_forge.py 里，这5个函数被作为参数传给 ADK（before_tool_callback=before_tool），由 ADK 自动触发。而在 valley 前端（forge/agent/service.py）里，是普通软件代码在同样的时刻手动调用这些函数。

同一段代码，同一个触发时机，不同的调用者——说明 Callback 没有魔法，就是函数。ADK 唯一多做的事是"保证绝不会忘记调用它"。

before_tool：决定脸是否改变的那一刻

png = (state.get("temp:_last_output_png") if mode == "latest"
       else state.get("temp:character_ref_png")
            or state.get("temp:provisional_ref_png"))
if png is None:
    png = await artifact_png(tool_context, seed)
state["temp:active_reference_png"] = png

它在操作 state——第6章那个共享字典。那个 or 决定优先级：先用正式锁定的 character_ref，退而求其次用临时的 provisional_ref，保证每次画图前一定有一张参考图。

Identity Lock：关键一行

picked = state.get("requested_reference") or canon
if state.get("identity_lock", True):
    return canon, canon_png, f"identity lock → overruled {picked}, anchored to {canon}"
return picked, picked_png, f"lock off → honoured {picked}"

picked 就是你在 valley 界面上点击选中的图。但第二行可以直接把它扔掉——只要 identity_lock 是开的，无论你点了什么，都强行换回 canon（你最初认领的那张图）。

两种模式，本质区别

每次给图像模型的输入只有两样：一张图 + 一句话。

模式发送的图发送的句子结果
⚓ 锁定开每轮都是最初那张 P₀全部装扮历史（"皇冠 + 披风 + 灯笼"）脸永远不变
◈ 锁定关上一轮的输出：P₀→P₁→P₂→P₃只有最新的那一件装扮脸慢慢漂移
⚠️ 为什么漂移很难发现？
第2轮时，模型不是在看你的原始生物，而是在看它上一轮"猜"出来的版本。任何微小的画错都会成为下一轮的"事实依据"，误差一点点累积——每次看起来都没什么问题，但 4-5 轮后对比最初，眼睛变圆了、嘴巴形状变了。这是"复印件的复印件"效应。

对比实验：grove vs grove_locked

  1. 在 grove 里认领 Mochi，然后说"给它戴顶金冠"——你得到一只全新的、戴着金冠的生物，Mochi 消失了。因为 grove 没有 generate_look，唯一会画图的 cast_candidates 每次都是重新召唤一只新的。
  2. 切换到 grove_locked，同样的操作——同一张脸，换上了金冠。打开 State 标签页：
    current_look   {"form": "a golden crown", "anchored_to": "canon", ...}
    anchored_to: "canon" 就是 before_tool 留下的收据。

三层控制力度——这章的精华总结

控制方式谁来保证可靠性
指令（"永远是可爱的动物"）模型，看心情低——模型可能不执行
你的点击/选择没有人——这只是一个请求低——可以被覆盖
Callback（identity lock）你的代码，每轮必然执行高——没有例外
核心结论

指令是请求。Callback 是规则。

任何你输不起的东西，既不该只写在 prompt 里，也不该只靠一次点击来保证——它必须写进 Callback 里。
